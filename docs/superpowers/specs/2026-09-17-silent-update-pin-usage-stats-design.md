# 飞书日程 v2.1.3 设计：静默更新、窗口置顶与匿名使用统计

## 背景

当前版本已经具备 GitHub Release 更新检查、窗口置顶配置和“关于”页，但仍有三处不足：

- 启动检查到新版本后只显示 Toast，用户还需要手动进入更新弹窗并等待下载。
- 置顶入口只存在于主窗口溢出菜单，系统托盘和设置页没有统一入口。
- “关于”页没有使用人数或活跃用户数据，仓库也没有统计服务端。

本设计覆盖上述三项需求，并把统计服务纳入仓库，部署到现有 HP 腾讯云。

## 目标

1. Windows 打包版在后台检查、下载并校验新版本，尽量不打断用户；下次启动时自动替换并进入新版本。
2. 用户可以在主窗口菜单、系统托盘和设置页统一切换“窗口置顶显示”。
3. 应用使用匿名安装 ID 上报低频心跳，统计累计独立安装用户和近 30 天活跃用户，并在“关于”页展示。

## 非目标

- 不统计飞书账号、用户名、日程内容、事件数量或飞书 API 行为。
- 不采集 IP 地址、设备指纹、MAC 地址、主机名或操作系统序列号。
- 不实现 macOS `.app` 的自动替换；macOS 仍使用现有更新提示与 Releases 下载。
- 不实现强制更新，不因统计或更新检查失败而阻塞应用启动。

## 方案概览

### 1. 后台静默更新

Windows 冻结版采用“后台暂存、下次启动安装”的两阶段更新：

1. 启动 4 秒后继续使用现有 `CheckWorker` 检查 GitHub Release。
2. 若发现更新、运行于 Windows EXE、Release 中存在 EXE 资产且提供了 SHA-256：
   - 后台下载到 `sys.executable + ".pending"`；
   - 校验 SHA-256；
   - 写入 `sys.executable + ".pending.json"`，记录版本、资产名、哈希和暂存时间；
   - 通过现有 Toast 显示“新版本已准备好，将在下次启动时安装”，不弹出模态框。
3. 应用下次启动时，在创建主窗口前调用更新安装函数：
   - 校验 pending 文件存在、版本比当前版本新、SHA-256 正确；
   - 将当前 EXE 改名为 `.old`，把 pending 文件替换为当前 EXE；
   - 立即启动新 EXE 并退出当前旧进程；
   - 新版本启动时清理 `.old` 和 pending 元数据。
4. 若下载、校验、替换或权限检查失败，删除不完整文件，记录日志，并继续正常运行旧版本。

源码运行、macOS、缺少 EXE 资产或缺少 SHA-256 时，不执行静默替换。保留现有 Toast 和手动更新弹窗作为降级路径，避免不安全或不支持的自动更新。

现有设置项“启动时自动检查更新”继续控制整个后台流程。用户关闭后，不检查、不下载、不暂存。

### 2. 窗口置顶

配置键继续使用 `pin_to_top`，默认保持 `true`。

新增和统一以下入口：

- 主窗口溢出菜单：保留现有“窗口置顶”复选项。
- 系统托盘菜单：新增可勾选的“窗口置顶”。
- 设置页“外观”：新增“窗口置顶显示”复选框。

三个入口共享同一个状态。任意入口切换后立即更新窗口 flag、写入 `config.json`，其余入口下次显示时同步勾选状态。切换时保持窗口当前位置和尺寸，不重新居中。

### 3. 匿名使用统计

#### 客户端

首次启动时生成 32 位随机十六进制 `install_id`，保存在现有 `config.json`。该 ID 不来自登录信息或设备信息。

应用启动后延迟发送一次心跳，请求体只包含：

```json
{
  "install_id": "随机 UUID 十六进制",
  "version": "2.1.3",
  "platform": "win32"
}
```

心跳在后台线程执行，超时后静默放弃。服务端响应同时返回最新统计值，客户端无需额外请求。

“关于”页打开时异步请求统计接口：

- 请求中：显示“正在获取使用数据…”
- 成功：显示“累计使用人数”和“近 30 天活跃”
- 失败：显示“统计暂不可用”，不影响其他内容

说明文案明确写出“匿名统计，不包含飞书账号、日程内容和设备标识”。

#### 服务端

在仓库新增 `stats_server/`，使用 Python 标准库 HTTP 服务与 SQLite，避免给桌面应用增加运行时依赖。

接口：

- `GET /health`
- `POST /v1/heartbeat`
- `GET /v1/stats`

数据库表 `installs`：

- `install_hash`：`sha256(install_id + server_pepper)`，主键
- `first_seen`：首次心跳 UTC 时间
- `last_seen`：最近心跳 UTC 时间
- `app_version`：最近版本号
- `platform`：`win32` 或 `darwin`

统计口径：

- 累计使用人数：`installs` 唯一行数
- 近 30 天活跃：`last_seen >= now - 30 days` 的唯一行数

服务不记录 IP 地址，不在数据库中保存原始 `install_id`。Nginx 对该路径关闭 access log，并把请求限制为小体积 JSON。

#### 部署

- 服务监听 `127.0.0.1:8010`，由 systemd 常驻。
- HP 上的 Nginx 在 `www.airtraffic.site` HTTPS 配置中新增：
  `location /feishu-calendar-stats/`
- 客户端固定访问：
  `https://www.airtraffic.site/feishu-calendar-stats/v1/heartbeat`
  和同前缀的 `/v1/stats`。
- SQLite 数据文件放在 `/home/ubuntu/feishu-calendar-stats/stats.db`。

## 组件边界

- `updater.py`：负责版本解析、后台检查、下载、校验、暂存和启动前安装。
- `main.py`：负责启动时机、异步 worker 生命周期、Toast 和统计心跳调度。
- `settings_dialog.py`：负责外观页置顶开关、关于页统计展示和状态文案。
- `main_window.py`：负责置顶状态的实际应用和菜单同步。
- `usage_stats.py`：只负责安装 ID、请求体构造、HTTP 请求和响应解析。
- `stats_server/app.py`：只负责 HTTP 路由、输入校验和 SQLite 聚合。

这些模块通过明确的函数或信号连接，避免把网络、数据库和窗口逻辑塞进单个文件。

## 错误处理

- 更新检查、下载和统计请求均不得阻塞 GUI 线程。
- 任何网络失败都不弹错误对话框，只记录日志或显示非阻塞状态。
- 静默更新只有在哈希校验成功后才能进入 pending 状态。
- pending 文件在应用下一次启动前始终保持可丢弃状态，失败时旧 EXE 可继续运行。
- 统计服务端对非法 JSON、超长字段、非法平台和无效安装 ID 返回 400。
- Nginx 或统计服务不可用时，关于页显示降级文案。

## 测试

### 客户端

- 配置：`install_id`、置顶配置可持久化，非法值回退默认。
- 统计：首次生成 ID 后复用；心跳请求和统计响应解析正确；超时返回不可用。
- 静默更新：暂存文件写盘、哈希校验、pending 元数据、启动前替换、失败恢复旧 EXE。
- 设置页：置顶开关写入配置并通知主窗口；关于页在成功、加载、失败三种状态正确展示。
- 托盘与主窗口：置顶入口状态一致，切换后窗口 flag 同步。
- 现有全部离线测试继续通过。

### 服务端

- 同一安装 ID 多次心跳只计为一个累计用户，并更新 `last_seen`。
- 不同安装 ID 计为不同用户。
- 30 天窗口外的记录不计入活跃用户。
- 数据库保存的是哈希，不保存原始安装 ID。
- 非法请求返回 400，健康检查和统计接口返回预期 JSON。

### 发布验证

- 本地运行完整 `pytest`、编译检查和 Windows 打包。
- 部署统计服务后，通过真实 HTTPS 地址执行心跳与统计请求。
- 推送 `v2.1.3` 标签，等待 GitHub Actions 全部成功。
- 验证 Release 中存在 Windows EXE、macOS zip 和 SHA256SUMS。
- 用最新 Release 数据模拟旧版本启动，确认后台暂存和下次启动替换流程可执行。

## 发布影响

- 版本号更新为 `2.1.3`。
- README 的功能、隐私说明和统计接口部署方式同步更新。
- 发布标签使用 `v2.1.3`，沿用现有 GitHub Actions 自动构建和 Release 上传流程。
- 统计服务先于客户端发布部署，避免新版本首启请求 404。
